# SCADA Desktop

Прототип Windows-клиента для существующего Java SCADA-сервера. В одном репозитории
находятся React GUI и локальный Electron/gRPC-шлюз; сам Java-сервер остаётся внешней
системой.

## Что реализовано

- подключение к адресу `host:port` по plaintext gRPC;
- `OpenSession`, metadata `TokenSession` и подписка `subscribeCommandChangeTM`;
- отображение текущих TI/TS в таблице и последних 250 событий в журнале;
- флаг одновременно в signed decimal и 16-битном hex (`-1 (0xFFFF)`);
- техническая форма `CHANGE_TM` для TI/TS;
- фиксированный UUID получателя `00000000-0000-1000-a000-000000000001`;
- автоматическое переподключение с новой сессией и exponential backoff;
- сохранение последнего адреса в `%APPDATA%/scada-desktop-client/settings.json`;
- закрытие окна в системный трей; явный пункт «Выход» закрывает gRPC-сессию;
- Windows x64 installer через Electron Forge / Squirrel.

## Архитектура

```text
React renderer
      │ узкий типизированный IPC API
      ▼
Electron preload (contextBridge)
      │
      ▼
Electron main: ScadaGateway + память + reconnect
      │ @grpc/grpc-js / user.proto
      ▼
Внешний Java SCADA server
```

Renderer работает с `contextIsolation`, без Node.js и без прямого доступа к gRPC.
Слой `ScadaGateway` не зависит от конкретного хранилища: текущий `Map` позднее можно
заменить репозиторием на SQLite/другую БД, не меняя IPC-контракт и компоненты UI.

## Запуск разработки

Требования: Windows, Node.js `>=22.12`, npm.

```powershell
npm ci
npm start
```

Dev-сервер намеренно занимает `127.0.0.1:5173` в режиме `strictPort`: перед повторным
запуском завершите предыдущий экземпляр через пункт «Выход» в трее.

В поле адреса укажите тестовый Java-сервер, например `127.0.0.1:9090`, затем нажмите
«Подключиться». TLS и авторизация в текущем Java-контракте отсутствуют.

## Проверки

```powershell
npm run typecheck
npm test
npm run package:win
```

Тесты включают in-process gRPC-сервер на том же `proto/user.proto`: проверяются открытие
и закрытие сессии, metadata, входящая телеметрия и точная wire-форма команды.
Они находятся отдельно от рабочего кода в `tests` и зеркалируют структуру `src`:
например, `tests/main/scada` соответствует `src/main/scada`.

## Сборка установщика

```powershell
npm run make:win
```

Результат появится в `out/make/squirrel.windows/x64/SCADA-Desktop-Setup.exe`.

## Важные ограничения прототипа

- Начального snapshot RPC пока нет. Таблица сначала пуста и содержит только новые
  события после подключения.
- Данные находятся только в памяти. При reconnect они остаются видимыми, но считаются
  устаревшими до нового события; после перезапуска приложения исчезают.
- Реально поддерживаются TI и TS. Java-конвертер приводит TS к signed byte, поэтому UI
  ограничивает его диапазоном `-128…127`.
- `response_code = 0` от `sendCommandChangeTM` означает только «сервер принял в
  обработку», а не исполнение командой оборудования.
- Команда не повторяется автоматически после timeout/transport error: сервер мог успеть
  принять её, поэтому повтор создал бы риск дубля.
- Plaintext gRPC подходит только для тестового/доверенного сегмента сети. TLS,
  пользователи, роли, аудит, история и автообновление — отдельные следующие этапы.
- Прототипный installer пока не подписан сертификатом; Windows может показать
  предупреждение SmartScreen. Подпись нужна перед распространением пользователям.

Исходный protobuf-контракт сохранён по полям и номерам. Импорты Google protobuf в
локальной копии переставлены перед `extend`, потому что актуальный Node proto-loader
строго проверяет порядок деклараций; на wire-совместимость это не влияет.
